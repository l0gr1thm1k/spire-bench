# M1: one game end to end

A bot written against the library plays a full A10 game on the real
headless game, through the gateway, over a WebSocket on localhost. The game
ends at `game_over`, the result goes into SQLite, and the transcript is saved.
Replaying the transcript's moves into a fresh game reaches the same end.

## Try it

```
uv run python -m spirebench.gateway                   # terminal 1: ws://127.0.0.1:8765, token "dev"
                                                      # (--token TOKEN:OWNER for more owners)
uv run python tools/random_bot.py --episodes 3        # terminal 2
```

Results land in `data/gateway/gateway.sqlite` and
`data/gateway/transcripts/<episode>.jsonl.zst`, both ignored by git.

## What's in it

| Part | File | What it does |
|---|---|---|
| Protocol v0 | `schema/protocol-v0.json`, `src/spirebench/protocol.py` | Every message as JSON Schema: `hello`, `welcome`, `start`, `decisions`, `actions`, `errors`, `episode_end` |
| Observation | `src/spirebench/gateway/observe.py` | Removes the `rng` block, turns the draw pile into counts, removes enemy AI state |
| Episode | `src/spirebench/gateway/episode.py` | One game: the open decision, its numbered legal actions, the moves made, the outcome |
| Gateway | `src/spirebench/gateway/server.py` | WebSocket server; token check, starts games, checks each action, sends the next decision or the end |
| Store | `src/spirebench/gateway/store.py` | SQLite rows for agent versions and episodes; one zstd JSON-lines transcript per episode |
| Library | `src/spirebench/client/` | `Agent` (`act` or `act_batch`), `RandomAgent`, `Client.run`, and `resolve`, which turns an index, an action or matching fields into exactly one legal action |

A transcript is about 700 bytes for a 40-move game (613 to 855 bytes for 23
to 63 moves in a test run): the episode key and the
moves, because the seed replays exactly, plus a header naming the engine the
game ran on: the build, SHA-256 hashes of the game DLL (as shipped and as
patched) and of the harness DLL, the harness commit and the schema version.
Without those, a replay can't be checked after a harness update (Thomas
Friedel's review).

## What the tests show

Each guard was checked by planting the fault and watching its test fail:

| Planted fault | Caught by |
|---|---|
| The `rng` block left in the observation | the end-to-end test |
| Hidden fields filtered at the top level only | the mid-fight card pick test (see below) |
| A game whose harness died left open instead of ended | the harness-crash test |
| Starts sent back to back not counted until their games boot | the in-flight limit test |
| Any token allowed to play under any agent version | the agent-owner test |
| The game limit counted per connection, not per owner | the more-connections test |
| A finished game's slot never given back | the more-connections test |
| No cap on games across all owners | the gateway-cap test |
| One move left out of the saved transcript | the end-to-end replay, and the scripted-game transcript test |
| An out-of-range `action_id` passed to the game instead of refused | the `illegal_action` test |
| A transcript written without the engine identity | the end-to-end test |
| The library ignoring every `rejected`, so a refused start hangs | the agent-version-held-by-another test |
| The library stopping on a dead game's `internal` | the void-and-play-on test |
| An unexpected error from the game left open | the unexpected-failure test |
| A failed start not reported, or not giving back its harness and slot | the fails-after-boot test |
| Starts admitted out of order | the admission-order test |
| A harness that won't close stopping the result from being recorded | the will-not-close test |
| A failed write keeping the game slot | the cannot-be-written test |
| `true` accepted as a number | the boolean test |
| A missing shipped DLL recorded as the patched DLL's hash | the engine identity test |
| Zero games accepted | the zero-games test |

The gateway's refusals are tested against a scripted game, so they need no
real game: a wrong token, an `action_id` off the list, an answer to an old
decision, a move the game refuses, and a bot that leaves mid-game (it loses).

## What the review caught

A Codex review of this branch found a real leak. When a card pick opens in
the middle of a fight, the harness puts the whole combat board inside it,
under `combat` (`RunSimulator.cs`, `["combat"] = InCombatBoard(player)`),
including `rng`, the ordered draw pile and enemy AI state. The first filter
only looked at the top level, so all of that would have reached the bot. The
filter now removes those fields at any depth.

It also found that a game whose harness died was never ended or scored, that
starts sent back to back could open more games than the limit, and that a
client leaving could close a harness while a move was still using it. All are
fixed: the gateway waits for calls in flight before it closes anything, and
each game is ended and recorded exactly once. It also found that any token
could play under another owner's `agent_version`, which would let one bot add
losses to someone else's streak. Each token now has an owner, and an agent
version belongs to the first owner that plays it.

A second Codex pass confirmed those fixes and found one more: the game limit
was counted per connection, so one owner could open many connections and
start 64 harness processes on each. The limit is now per owner across all
their connections (`max_in_flight`, default 64), with a cap for the whole
gateway (`max_games`, default 128).

### The third review: bugs and code quality

A third review ran after the PR went up: Codex looking at bugs and code
quality, my own Claude pass, and four cleanup reviews (reuse,
simplification, efficiency, altitude). The two earlier passes only looked
for bugs, races and leaks.

It found four real bugs:

- **The library hung on a refused start.** The gateway also uses `rejected`
  for an agent version that belongs to another owner, and the library ignored
  every `rejected`. Now an error that names an episode belongs to that game,
  and the gateway follows it with a new decision or the game's end. An error
  with no episode is about a request, so the library raises instead of
  waiting.
- **One dead harness cost a bot all its other games.** The library raised on
  `internal` before reading the `episode_end(void)` that follows it, then
  disconnected, so every other open game counted as a loss. It now plays on.
- **An unexpected failure while starting a game reached nobody.** The client
  got neither an error nor a game. Each start or action that fails now sends
  `internal` to the client.
- **A failed write left a game half-recorded.** The episode was released
  before its transcript and row were written. Closing the harness and
  recording the result now each catch their own failure, so one can't stop
  the other.

A Codex pass over those fixes found the same kind of problem one level
deeper, and those are fixed too:

- **The game failing in an unexpected way** (not a harness error) now voids
  that game and ends it, instead of reporting an error and leaving it open.
- **A start that fails after its game boots** closes the harness and gives
  the slot back.
- **Starts are admitted in the order they arrive.**
- **Each store write is a transaction,** so a failed write can't be
  committed later by someone else's.

It also tightened smaller things:

- `true` is no longer accepted as a number in `count`, `ascension`,
  `action_id` or `seq`.
- `metadata` must be an object.
- `episodes=0` is refused before connecting.
- `Client.run_async` is there for notebooks and async apps.
- The end-to-end replay now checks the outcome and the act, not just the
  floor.
- The engine header records a missing shipped DLL as missing. Before, it
  quietly used the patched DLL's hash. It also records `harness_dirty`, so a
  harness with local edits isn't passed off as its commit.

Cleanups:

- SQLite writes, transcript compression and the observation filter now run
  off the event loop. SQLite uses WAL.
- One function builds an action for both the legal-action list and the
  transcript, so the two can't drift apart.
- `Game` moved to the worker, so `legal_choices` is typed again.
- The game version, message size limit, practice key and maximum ascension
  each live in one place.
- The import-order workaround around `__version__` is gone.

Skipped, with reasons:

- **Typed decision classes** (`TypedDict`) for bot authors: worth doing once
  the observation schema is closed (M2 slice 5).
- **The schema shipped inside the package:** `load_schema` still finds it
  only in a source checkout. Only the tests use it today.
- **`rejected` meaning three things:** the error rule above settles the
  library's side. Splitting the code is a protocol change, left for M2.
- **Inlining small methods** (`_end`, `_void`): M2 rewrites those parts of
  the code.

## Decided for v0, open to change

- **Actions use the harness's verbs** (`play_card`, `choose_option`,
  `buy_card`, `select_map_node`, ...), with the harness's argument names
  (`card_index`, `target_index`). The plan's smaller vocabulary (`choose`,
  `buy`, cards by instance) waits until real adapters show what they need.
- **`action_id` is the action's position** in `legal_actions`.
- **A move the game refuses** gets `rejected`; the gateway drops it from the
  list and sends a fresh decision with the next `seq`.
- **An error that names an episode is about that game alone.** A new decision
  or the game's end follows it. An error with no episode is about a request,
  and the library stops on it.
- **A bot that disconnects loses its open games**, so quitting can't protect a
  streak.

## Not yet (M2)

- The observation filter removes known fields (a deny-list). M2 turns it into
  an allow-list, so a field the harness adds later stays hidden by default.
- `deadline_ms` is sent but not enforced.
- One decision per `decisions` message; the gateway doesn't batch across games
  yet, though the client already calls `act_batch` with whatever arrives.
- No reconnect or resume.
- **A big multi-card pick lists at most 64 selections**
  (`MAX_SELECT_CHOICES`), so some legal picks are missing from
  `legal_actions`. The fix is a structured `select_cards` answer the gateway
  checks against the pick's minimum and maximum, rather than listing every
  combination.
- **No backpressure.** Every incoming message becomes a task. M2 bounds the
  messages and actions a connection may have waiting.
