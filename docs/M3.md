# M3 plan: keyed dice and exact replay

This is the plan for M3. Slices 1 (gateway keys), 2 (keyed streams, on
v0.107.1) and 3 (replay and restore) are built; slice 4 (distribution checks)
is not, so nothing is scored yet. Deadlines and
the illegal-action cap are M2 work; when they land they must end the game as a
loss, per the table below. M3 is the milestone after which
games can be scored, so it has to close every way a bot could know or
influence the dice. [PLAN.md](PLAN.md) has the short version.

## What M3 has to guarantee

1. **A bot can't know the dice.** Before a game ends, nothing the bot receives
   or can compute pins down any future random outcome. Searching ahead while
   guessing the dice is allowed. Working them out is not.
2. **A bot can't redo a game.** Each game is played once, under a key the bot
   never chose. A crash on our side never hands the bot a second try.
3. **The operator can't pick the dice.** Every key is fixed before its game
   starts, and anyone can check that afterwards.
4. **Every game replays exactly**, from a transcript, on another machine.

## Why the current design falls short

**The seed is revealed, and it is the whole game.** `episode_end` sends
`episode_key`, which is the raw seed passed to `start_run`
(`server.py:201`, `server.py:270`). The seed is also written to SQLite when
the game starts (`store.py:86`). Today the reveal is harmless only because
seeds are never reused and nothing is scored.

**On v0.107.1, hiding the seed is not enough.** The game hashes the seed
string to a 32-bit `uint` (`RunRngSet.Seed = (uint)GetDeterministicHashCode(seed)`).
Every stream is that number plus a hash of the stream's name, fed through
Splitmix64 into Xoshiro256**. So the whole game comes from 2^32 possibilities,
however long the seed string is. We timed a search of all 2^32 seeds that
replays the first four draws of one stream: **1.6 seconds** on a 24-core
desktop. Four `NextInt(10)` draws left 429,208 candidates, the true seed among
them. A first shuffle or the Neow options cut that to one.

A bot that does this knows every future draw after the first screen. So the
fix the PLAN sketches as gateway-only, an HMAC-derived seed string passed to
the game's own generator, does not work on v0.107.1. The keyed streams have to
replace how the game derives its seeds, not only where the seed comes from.

**v0.111.0 is 64-bit but not keyed.** It hashes with XxHash64, so the master
seed is 64 bits and a full search is out of reach. Every stream is still
`seed + hash(name)` from one number, though, and Xoshiro256** is a fast
generator, not a cryptographic one. Its outputs aren't built to hide its state.
We haven't measured a state-recovery attack on the game's truncated draws, and
we don't plan to rely on there being none.

**Void games dodge losses.** A game that hits a harness error, a screen with
no listed moves, or an unknown screen is voided (`episode.py:73-113`). A void
doesn't count. If a bot can steer into one, it can drop a game it was going to
lose.

**The keyed streams aren't public yet.** M3 as written waits on Thomas's
private branch. The v0.111.0 generator there is still a stub.

## Design

### Keys

Each season has a secret: 32 random bytes, kept outside the repository and the
database, readable only by the gateway.

```
episode_key = HMAC-SHA256(season_secret, "spirebench/episode/v1" | season | agent_version | number)
practice_key = HMAC-SHA256(season_secret, "spirebench/practice/v1" | season | agent_version | number)
```

- Keys are 256 bits. Nothing about a key is ever narrowed to the game's
  32-bit seed.
- `number` is the agent version's episode count, taken in the same SQLite
  transaction that records the game's start. That makes it crash-safe and
  never reissued. `Store.begin` picks it and inserts the row in one statement.
- The store keeps `(season, agent_version, number)` and never the key. A
  leaked database or transcript of an unfinished game gives nothing away.
- Practice keys use their own label, so a practice key can never equal a
  scored one.

### Keyed streams in the harness

The harness takes the 32-byte key in place of a seed string, and refuses a
seed string.

- **One generator per stream.** Each stream's key is
  `HMAC-SHA256(episode_key, "spire-bench stream v1\0" | seed)`, where `seed`
  is the 64-bit seed the game itself derives for that generator (little
  endian). The game already gives each stream its own seed (the run seed plus
  a hash of the stream's or content's name), so this covers the run streams,
  each act's map RNG and every per-content `Rng(seed + hash(name))` site
  without a list of names to keep in step with the game. The game is handed a
  public seed string, `SPIREBENCH`, the same for every game; only the episode
  key separates games. Two generators the game seeds alike share a stream,
  exactly as they do in the unmodified game. Seeing one stream's draws tells
  you nothing about another stream.
- **`Rng.Chaotic`**, the game's clock-seeded generator (cosmetics, text
  variants, some monster draws), becomes one keyed stream per game on
  `HMAC-SHA256(episode_key, "spire-bench chaotic v1")`.
- **One key per process.** A harness takes one key and refuses a second; a
  generator opened before the key that draws once it is set raises.
- **A cryptographic generator, not a keyed Xoshiro.** Each stream is
  ChaCha20, with the stream key as the key and the draw number as the counter.
  The game's 64-bit draw (`NextULongInner`) becomes the next 64 bits of
  ChaCha20 output. Every `Next*` the game builds on top of that keeps its own
  derivation. The game's draws come from a uniform 64-bit source either way, so
  the distributions don't change. ChaCha20 costs a few nanoseconds per draw.
- **The unkeyed-draw guard.** After boot, any randomness not drawn from a keyed
  stream raises inside the harness: a `Rng` built from an integer seed,
  `System.Random`, or Godot's RNG. The episode is voided as a server fault (see
  below), and the fault is a bug to fix before the season.
- **Card instance ids** come from `HMAC-SHA256(episode_key, "ids")`, as
  [PLAN.md](PLAN.md) already says, if they turn out to be drawn rather than
  counted. Not yet checked.

**Built (slice 2).** Thomas's branch was not public, so the patch lives here:
`harness/build_keyed.sh <version>` builds `KeyedRng.dll` (the key schedule and
an RFC 8439 ChaCha20 with a self-test) and rewrites the pinned harness with
Mono.Cecil (`harness/KeyedPatcher`) into `build/keyed/<version>/`. `MegaRandom`
draws through the key; `System.Random`, Godot's `GD.Rand*`,
`RandomNumberGenerator` and the dev console's clock-seeded encounters are
guarded (13 call sites in `sts2.dll`, none in the harness). `MegaRandom.NextBytes`
is refused rather than keyed. `--plant-unkeyed-draw` builds a copy with a
planted `System.Random` for the guard's test. The gateway passes the key, and
the engine header hashes the patched DLLs and `KeyedRng.dll`. Verified on
v0.107.1 only (`tests/test_the_keyed_harness_deals_the_game_its_key_decides.py`
with `SPIREBENCH_GAME_VERSION=v0.107.1`): the same key deals the same game in
two processes, one flipped key bit deals another, a seed string and a second key
are refused, and the planted draw stops the game. v0.111.0 is not installed
here, so the patch is unbuilt and unchecked there.

**Checking the keyed build.** Two tools look for randomness the key does not
decide, one reading the code and one playing it. Both are v0.107.1 only so far.

- `harness/audit_keyed.sh <version>` (Mono.Cecil, `harness/KeyedAudit`) lists
  every call in the keyed `sts2.dll` and harness to the clock, `Guid`, a hash, a
  generator other than the keyed one, or the seed, and whether it is guarded.
  Each unguarded call must have a reviewed reason in
  `harness/keyed_audit_allowlist.json` (132 on v0.107.1: UI and network time,
  stream naming, timestamps, hash codes used as dictionary keys, cosmetics).
  `tests/test_the_keyed_harness_has_no_unreviewed_randomness.py` fails on a new
  call and on one that went away. Removing one reviewed entry turns it red.
- The keyed harness takes only the commands the gateway sends (`start_run`,
  `action`, `legal_actions`, `quit`) and only their known fields. `rng_probe`,
  `roll_acts`, `get_state`, `dump_*` and the rest are refused before they run.
- `tools/fuzz_keyed.py --version <v> --keys N` plays random games under random
  keys and checks three things. **Determinism:** the same key and moves in two
  fresh processes show the same observation digest at every step. **Streams:**
  this needs the trace build, `harness/build_keyed.sh <v> --trace-streams`,
  which logs each stream opened. A one-bit key flip must change every stream's
  first draw, by about 32 of 64 bits on average. **Leaks:** an observed field
  that varies with the seed in the upstream build but shows the same value
  under every key, past a 10⁻³ chance level, is drawn from something public.
  `tests/test_the_fuzzer_finds_what_the_key_does_not_decide.py` runs it briefly
  and shows that the leak check fires when every game gets one key. On v0.107.1
  with 12 keys, all checks passed:
  - 12/12 replays were identical.
  - 293 stream pairs changed by a mean 32.0 bits (min 20, max 42).
  - Of 537 seed-varying fields, none was fixed under the key.

  Random players die in act 1, so this covers act 1 only.
- **Shared monster streams.** The trace shows that the monsters of one combat
  (`CombatState.CreateCreature`) can open the same seed: 2 to 5 creatures,
  identical draws. The unmodified game does the same, so the key keeps it
  hidden but does not decorrelate it. The fuzzer reports it and does not fail on
  it.

**Still open:** the v0.111.0 patch, audit and fuzz; card instance ids (any id
drawn from an unkeyed generator would trip the guard, but a counted id has not
been checked); `observe.py` filters by a block-list, so a new harness field
reaches the bot unless it is listed; a fuzz that reaches acts 2 and 3.

### Commit and reveal

This moves into M3 from after M5. It is a few lines, and without it nobody can
check guarantee 3.

- **Season start:** publish `SHA-256(season_secret)` and the season id.
- **Game start:** each game opens with `episode_start {episode, number, commit}`,
  `commit = SHA-256(episode_key)`, sent before the worker boots.
- **Game end:** `episode_end` reveals `episode_key` to its owner, as now. The
  client library checks it against `commit` and refuses a mismatch.
- **Season end:** publish the secret. Anyone can then recompute every key from
  `(season, agent_version, number)` and replay every game.

Revealing a key to its owner is safe because keys are per agent version and
never reissued. A revealed key says nothing about any other game, and the
owner can't replay it for credit.

### Ending a game

| Cause | Result |
|---|---|
| Win or death | as played |
| Bot disconnects, misses the game deadline, or hits the illegal-action cap | **loss** |
| Worker crash or host error | **restore**: a new worker replays the same key and actions, checks the observation digest, and the game goes on from where it was. The bot never chooses again |
| Restore diverges, the unkeyed-draw guard fires, or the screen is unknown | **server fault**: not scored, listed on the results page against the build, and fixed before the season |

No outcome the bot can cause leaves a game unscored. A bot that wants out of a
bad game can only take the loss.

### Transcripts and the replay tool

A transcript holds `(season, agent_version, number)`, the commit, the engine
header from M1, the moves, and a SHA-256 digest of each observation. Digests
cost 32 bytes a move and show the exact step where a replay goes wrong.

`python -m spirebench.replay <transcript> --key <hex>` refuses an engine
header that doesn't match the local harness, naming the field. It replays the
moves under the key, compares every observation digest, and reports the first
step that differs, or `identical`. Operators get the key from the secret, and
owners get it from `episode_end`. After the season, anyone can.

## Slices

1. **Gateway keys.** The season secret, key derivation, crash-safe numbering,
   commit and reveal, storing no keys, and the end-of-game table. This needs
   no harness change. Built.
2. **Keyed streams.** Our own patch: ChaCha20 per stream, the guard, and
   refusing seed strings. Built and verified on v0.107.1; v0.111.0 still to
   build and check.
3. **Replay and restore.** Observation digests, the replay tool, and restoring
   a crashed game.
4. **Distribution checks.** The keyed game against the real one.

## Done when

Each guard is shown to fail by planting its fault:

- A transcript replays to the identical game on a different machine,
  including games that reach acts 2 and 3.
- The same transcript with one action changed diverges, and the tool names
  the step.
- A planted unkeyed draw voids its game as a server fault.
- The harness refuses a seed string, and a planted 32-bit truncation of the
  key is caught: flipping any one bit of the episode key must change the
  first draw of every stream.
- Two games with the same agent version and number are impossible, including
  across a gateway restart in the middle of a game.
- A worker killed mid-game is restored and ends exactly as an uncrashed replay
  of the same moves.
- A bot that disconnects, times out or hits the illegal-action cap gets a
  loss, never a void.
- The revealed key matches the commit, and a forged reveal is refused by the
  library.
- The keyed game matches the real one in distribution over 10,000 games, by a
  chi-square test at p > 0.01: where a marked card lands in the shuffle, card
  reward rarity, and enemy intent frequency per encounter.
- The M2 suite still passes.

## Open decisions

- **Shared boards.** If every agent version played the same keys for a given
  number, comparisons would be paired: the same boards for every bot, with far
  less noise. The catch is that keys could then only be revealed at season end,
  not when each game ends. Proposed: keep per-version keys for M3, and decide
  for season 0 when scoring is designed in M5.
- **Who holds the season secret** when the gateway moves to the cloud.
