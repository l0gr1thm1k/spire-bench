# M0: the headless game runs here, and what a run costs

November 11, 2026. Harness: spire-mentor `Sts2Headless` at `368d4e9b`, Release
build, game v0.111.0 from a local Steam install. Machine: Threadripper 3960X
(24 cores, 48 threads), shared with another job (a Rust build) during the runs.

## What works

- The harness builds from our own install and plays A10 runs for all five
  characters over its JSON-lines pipe. The tool is `tools/m0_measure.py`.
- **Same seed, same game.** The same 50 seeds played under three different
  .NET settings gave identical games: 6,799 actions and the same floors each
  time. `tests/test_a_seeded_game_replays_to_the_same_end.py` checks this, and
  also checks that a different seed gives a different game.

## What we found

1. **One game per process.** A second `start_run` in the same process fails
   with "State is already set". spire-mentor's own full-run tools also start
   a fresh process per run, so every game pays the startup cost.
2. **Startup costs about 1.25 s of CPU** per game, counting the process boot
   and `start_run`, with the settings below.
3. **CPU per action is about 5.6 ms** on greedy runs (fresh processes, mostly
   act 1), and 4.8 ms after the first 200 actions. Short random A10 games,
   about 45 actions each, stay colder, at 8.9 ms. Thomas's 1.3 ms
   was measured after 220 fights in one warm process, which we can't reach
   while each game needs its own process.
4. **.NET settings matter.** `DOTNET_TieredPGO=0`, `DOTNET_TC_QuickJitForLoops=1`
   and `DOTNET_ReadyToRun=1` cut CPU per action from 6.5 to 5.4 ms on the same
   50 games. Turning tiered compilation off entirely made startup slower
   (1.8 s) and was worse overall. `HeadlessGame` now sets the faster three by
   default.
5. **Wall time per action is about 15 ms** per process, about three times the
   CPU time. The game thread spends most of its time waiting, so several
   processes fit on one core.
6. **Random players die early.** At A10 they die around floor 4, and a greedy
   player that always plays a card dies around floor 7. Neither reaches act 2,
   so act 2 and act 3 play hasn't been exercised yet.

## How long a real run is

Measured from the 40 human A10 wins in our replay corpus (v0.111.0): about
**980 player actions per winning run** (median 986, range 619 to 1,412). That
count covers card plays, turn ends, decisions and map moves. Losing runs are
shorter. cygn's earlier estimate was 1,500.

## What an entry costs

Per run: 1.25 s of startup plus 1,000 actions at about 5.3 ms, which comes to
about 6.5 CPU-seconds. That is an upper bound, because most runs are losses and end
early. One entry of 5,000 runs is then 5,000 × 6.55 s ≈ 9.1 CPU-hours.

Priced on AWS `c7a.large` (2 vCPUs, each a full AMD core), Linux, US East,
as listed on [instances.vantage.sh](https://instances.vantage.sh/aws/ec2/c7a.large)
on November 11, 2026: $0.10264 per hour on demand and about $0.034 per hour
spot, so about $0.051 and $0.017 per vCPU-hour.

| | CPU time | On demand | Spot |
|---|---|---|---|
| One run | ~6.5 s | | |
| One entry (5,000 runs) | ~9.1 vCPU-hours | ~$0.47 | ~$0.15 |
| Ten entries | ~91 vCPU-hours | ~$4.70 | ~$1.50 |

Two caveats on the price. The CPU time was measured on a Threadripper 3960X
(Zen 2, with SMT), not on a `c7a` (Zen 4, no SMT), so the per-action cost on
AWS will differ; it should be measured there before the number is quoted as
more than an estimate. Spot prices move from hour to hour.

The proposal estimated 37.5 core-hours per entry. Our estimate is about four
times lower, and a 16-thread box would score one entry in well under an hour.

## Caveats

- Per-action cost was measured mostly in act 1, on a shared machine, with
  cold processes. Act 2 and act 3 fights may cost more per action.
- Wall-clock throughput depends on how many processes run per core. That
  should be measured on a quiet machine before sizing a host.

## Review fixes before commit

A cross-model review (Claude and Codex) caught three measurement errors, which
are fixed in this branch:

- Startup CPU had started counting after the process booted. It now includes
  the boot.
- Wall time had included closing the game and launching the next process. It
  now stops when play ends.
- The shop filter read fields the harness doesn't send, so every item looked
  affordable. It now reads `cost`, `is_stocked` and the player's gold, and it
  offers card removal. spire-mentor's own `run_parity.enumerate_choices` has
  the same shop filter, which is worth telling Thomas.
